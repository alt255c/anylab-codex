# Лабораторные AnyLogic

1. Вызови `tasks` с номером лабораторной и строкой варианта. Собери перечень заданий и моделей. По умолчанию выполняй всю лабораторную. У заданий без таблицы используй общее условие. Если таблица есть, но строки выбранного номера нет, используй данные пользователя или уточни только отсутствующие параметры. Открой оригинальный PDF по `official_pdf` для формул, рисунков и неоднозначных строк.
2. Вызови `templates` для этой лабораторной. Если задан путь к комплекту, передай его параметром `root`. Для готового ALP прочитай файл полей из `fields` и передай заполненные значения в `fill_model`. При необходимости доработай полученную копию с ресурсами. Используй `stage_template` для точного копирования без подстановки. В заданиях с `previous-task` используй уже выполненный проект указанного задания. Соблюдай композицию схемы, структуру агентов, блоки библиотек, правила имён и состав экспериментов образца; меняй то, что требуется выбранным вариантом. Если есть две модели одного задания, подготовь обе. При наличии DOCX из комплекта сохрани оформление, титул, последовательность разделов и подписи по его структуре. Прочитай [карточку лабораторной](references/labs.md) и сверяй изменения с официальным заданием. Импортируй локальные лекции и дополнительные материалы через `index` и бери фрагменты через `search`. Если готовой модели задания нет, используй установленный пример и укажи, на чём основан новый проект.
3. Проверь установку через `doctor`. Подготовь независимую копию каждого проекта с ресурсами. Используй `inspect` и `generate` для переименования, смены параметров и компоновки. Если нужны новые блоки, состояния, эксперименты или Java-выражения, редактируй копию ALP. При выборе языка сохраняй имена служебных классов и обновляй ссылки. Применяй цветовые изменения к сериям и осмысленные изменения геометрии там, где позволяет условие. Варьируй параметры согласно строке варианта. Учитывай пользовательские требования к трассе, палитре и наименованиям.
4. Собери и запусти каждый обязательный режим через `run` или `calibrate`. Укажи метрики числовыми Java-выражениями в контексте root. Для фиксированных сеток проверь число комбинаций и обязательных репликаций. Если замер не укладывается в бюджет, явно укажи это и согласуй изменение плана, если оно затрагивает требования задания. Для непрерывного режима отдельно проверь сценарий и задай конечный горизонт для сбора статистики. При ошибке проверь журнал IDE и повтори после исправления. Используй полный путь к модели и новые каталоги для прогонов.
5. Сделай кадры через `windows` и `capture`, когда окно отображает нужный этап. В ЛР4–ЛР6 при запросе видео открой сцену 3D и проверь движение в кадре, затем вызови `record` с HWND окна эксперимента. Для автоматического запуска отдельного 3D-показа можно вызвать `video`.
6. Если есть DOCX и `report_fields`, заполни поля, строки таблиц и места для снимков через `fill_report` по [структуре отчёта](references/report.md). При отсутствии заполняемого шаблона используй `report` и передай совместимый локальный образец в `spec.template`, если он доступен. Отдельно приложи ALP с ресурсами, протоколы и измерения. Отметь условия, где проверен только запуск или часть эксперимента. Перед выдачей проверь соответствие каждого задания его исходным данным и отсутствие дословного заимствования из чужих отчётов.

При долгом вызове MCP используй каталоги прогонов для диагностики. После тайм-аута сначала проверь result.json и окна, чтобы не запускать тот же эксперимент дважды.
